## 一、执行摘要与四主题评估雷达综述 (Executive Summary)

### 1.1 评估背景与技术架构

Antigravity 2.x 客户端构建于现代桌面技术栈：**Electron 32.x + Chromium 128 渲染内核 + React 18 并发渲染调度器**。美化插件系统通过 `patch/pixelTheme.js` 实现向 Electron 渲染进程的深层管道注入，通过 `install.ps1` 将加载钩子锚定在 `dist/utils.js` 与 `dist/ipcHandlers.js`，并通过热重载控制脚本 `switch-theme.ps1` 监听 CDP 端口（`DevToolsActivePort`），实现主题秒级免重启切换。

在物理高刷 **144Hz**（标准单帧耗时预算 **6.944 ms**）环境下，本评估结合全量 CDP（Chrome DevTools Protocol）差分追踪、`PerformanceObserver` 长任务捕获与 `requestAnimationFrame` 连续逐帧探针，对全部四大主题进行了 9 大动作场景的定量性能基准采集与全界面像素级视觉巡检。

### 2.2 144Hz 假性掉帧率辨析与真实高刷稳态确认

排查过程中发现一个显著的数据矛盾：在静止空闲稳态（`idleSteadyState`）和主聊天长列表滚动（`chatScroll`）场景中，四套主题的 144Hz 掉帧率普遍显示为 **45% ~ 59%**，然而其 60Hz 掉帧率却仅有 **0.0% ~ 0.8%**，且 Long Task 恒为 **0 个**。

#### 机制根因推导：
1. **系统计时器离散采样误差**：物理 144Hz 显示器的 VSync 硬件周期理论值为 $1000 / 144 \approx 6.9444\text{ ms}$。在 Windows 11 环境下，Chromium 的渲染合成器调度与 JavaScript 事件循环由于高精度时间戳（`performance.now()`）的微秒级离散化抖动，大量极为流畅的正常渲染帧其实际耗时落在 **6.95ms ~ 7.05ms** 之间。
2. **布尔硬过滤偏差**：测试脚本采用 `samples.filter(d => d > 6.944)` 进行判定。当一帧仅耗时 6.950ms（仅超出理论阈值 0.006ms，相当于 6 微秒的系统级时间片调度延迟）时，即被判定为“掉帧”。
3. **真实高刷性能定论**：从 P50（锁定在 **6.90ms ~ 7.00ms**）、P95（**7.00ms ~ 7.10ms**）以及 1 秒内稳定采集 141~144 帧的完整数据链可以确认：**在静止稳态与长列表惯性滚动场景下，Chromium GPU 合成器完全实现了 144Hz 原生满刷输出，不存在渲染瓶颈，该 144Hz 掉帧率属于统计学上的“假性掉帧”。**
4. **真实掉帧研判标准**：应以 **60Hz 严重掉帧率（$\Delta t > 16.67\text{ms}$）**、**最大滞后尖峰（Max Spike $>50\text{ms}$）** 以及 **主线程长任务（Long Tasks $>50\text{ms}$）** 作为用户可感知卡顿的真实度量基准。

#### 关键发现与机制剖析：

1. **根节点继承型 CSS 变量灾难**：
   原生 Antigravity 在最顶层容器 `<div class="h-screen w-screen flex flex-col bg-background">` 上声明了内联样式：
   ```css
   transition: --aux-pane-width 500ms, --sidebar-width 500ms;
   ```
   `--aux-pane-width` 是通过 `@property` 注册且具有 `inherits: true` 的继承型自定义属性。在 500ms 的抽屉滑动期间，每一帧变量数值的细微插值都会自顶向下向整个 DOM 树（实测 **2,050 个节点**）广播“样式已脏”，强迫 Chromium 渲染引擎在 700ms 窗口内触发 **39 ~ 65 次全树 RecalcStyle**，累计样式重算耗时高达 **167.5ms ~ 214.9ms**！
2. **Pixel 主题阻断规则的压倒性优势**：
   `pixel.css` 最早在代码中引入了强制阻断机制：
   ```css
   .h-screen.w-screen.flex.flex-col.bg-background {
     transition-property: none !important;
   }
   ```
   该规则切断了根变量的逐帧连续数值插值，使根变量在点击时直接突变到终点值。在此保护下，Pixel 在右侧栏收起时取得了全场最高的 **89.8 FPS**，P95 压制在惊人的 **14.0ms**（完全没有穿透 60Hz 帧边界），60Hz 掉帧率骤降至 **4.8%**。
3. **Doodle 主题并发列表动画引发的重排风暴**：
   在展开辅助栏时，`doodle-theme` 的 Layout 耗时飙升至 **133.69ms**（是 Pixel 的 2.3 倍），60Hz 掉帧率恶化至 **35.1%**，P50 帧间隔甚至破裂至 **13.9ms**。
   源码溯源锁定：`doodle.css` 第 1273 行仍挂载着 `[data-testid="conversation-list-sidebar"] .w-full.group { animation: doodle-expand-in 260ms ...; }`。当侧边栏尺寸变动时，会话列表中 30+ 个 DOM 节点并发执行位移动画，使得排队重排（Layout Queue）发生剧烈拥塞。
4. **右上角工具栏 `padding-right` 避让的物理轨迹**：
   右上角操作区通过内联属性动态避让原生 Windows 窗口控制按钮：
   ```html
   <div style="transition: padding-right 500ms var(--ease-expo-out); padding-right: max(8px, 36px - var(--aux-pane-width));">
   ```
   CDP 轨迹采样证实：其内边距平滑地由 36px（折叠态）过渡到 8px（展开态，总位移 28px）。由于该元素自身保持了独立的过渡属性，因此即使根节点变量瞬间阶跃，右上角按钮也不会发生硬跳，而是平稳滑移。

### 2.4 主线程阻塞与长任务 (Long Tasks >50ms) 深度溯源

除 CSS 几何变动引起的重排外，整个系统存在两处严重的 JavaScript 主线程长时间霸占（Long Task）：

#### 1. 设置弹窗（Settings Dialog）冷启动挂载阻塞 (173ms ~ 288ms)
- **实测表现**：无论何种主题，在点击设置按钮的一瞬间，主线程必被一个高达 **173ms ~ 288ms** 的巨型任务占满，最大帧间隔尖峰（Max Spike）突破 **229ms**。
- **根因剖析**：Antigravity 设置面板采用 React 18，但其内部包含了 7 大核心功能选项卡、14 个子表单面板、数十个 Combobox 选择器以及大量模型/快捷键配置项。在弹窗挂载时，React 采取了一次性同步递归构建全量子组件树的策略，导致纯 JS 执行耗时高达 180ms 以上。
- **“动画被吞噬”缺陷**：早期样式中弹窗入场动效仅设定为 **140ms ~ 150ms**。由于浏览器主线程在执行该 200ms+ 的长任务期间完全处于冻结状态，无法响应任何重绘事件，当主线程释放、准备绘制第一帧时，150ms 的 CSS 动画早已在虚拟时钟中超时结束。用户肉眼所见的不是优雅的弹出，而是界面卡死 1/4 秒后的“瞬态硬切突现”。

#### 2. 右侧辅助面板展开长任务 (118ms ~ 138ms)
- **实测表现**：展开动作首帧必然伴随 118ms ~ 138ms 的 Long Task，而收起动作的 JS 耗时由 177ms 锐减至 75ms ~ 119ms。
- **根因剖析**：展开动作不仅仅改变宽度，同时触碰了 React 条件渲染分支，同步实例化了辅助面板内部的 Monaco Editor 实例、代码高亮树与 Markdown AST 渲染器；而收起仅将容器移出视口或挂起，JS 负载大幅下降。

### 2.5 Chromium 合成层与 GPU 显存控制机制

在 GPU 渲染管线与显存（VRAM）方面，本插件体系展现了极高的工程约束水准：

1. **毛玻璃滤镜彻底清洗 (`backdrop-filter: none !important`)**：
   四大主题在通用重置区均无条件注入：
   ```css
   * {
     backdrop-filter: none !important;
     -webkit-backdrop-filter: none !important;
     text-shadow: none !important;
     background-image: none !important;
   }
   ```
   **技术收益**：Chromium 中最昂贵的开销是多重模糊滤镜，每次渲染都需要将屏幕像素回读至离屏 FBO（Frame Buffer Object），由 GPU 着色器执行大半径双重高斯模糊卷积，最后 Blit 回主缓冲。全局清洗使得客户端稳态 GPU 占用率稳定在 0.5% ~ 1.2% 的超低功耗区间。
2. **0 模糊硬边阴影 (`box-shadow: 4px 4px 0 #000`) 的栅格化优势**：
   全系统包含 70 ~ 105 处硬投影。在 Skia 绘图引擎中，`blur-radius: 0` 的阴影被退化为简单的 `SkCanvas::drawRect` 纯色几何矩形填充，完全绕过了高斯滤波核心，计算复杂度从 $O(r^2 \cdot W \cdot H)$ 降为 $O(1)$。
3. **合成层隔离与防显存爆炸 (`will-change`)**：
   - 整个界面严格将 `will-change` 限制在 4~8 处高频动态元素上（旋转指示器 `svg.animate-spin`、弹窗蒙层与主体）。
   - **扫描线显存克制实证**：`pixel.css` 第 1478 行与第 1802 行明确标注文档：*“扫描线那层是满屏的，故意不加 will-change：如果加了 will-change 会导致常驻一整屏合成层，占用 6MB+ GPU 显存”*。
   - 整个客户端常驻合成层数量牢牢锁定在 **12 ~ 18 个**，杜绝了数以千计合成层激增（Composited Layer Explosion）引起的显存耗尽。

## 三、四大主题 UI 视觉表现、动效规范与可视实用性评估 (R2)

### 3.1 六大核心交互场景全景评估

#### 场景 1：侧边栏伸缩 (Sidebar Collapse / Expand)
- **现状评测**：Pixel 主题在根变量阻断下收起极其流畅（89.8 FPS）；Doodle 因列表项并发动画导致展开时掉帧明显（Layout 133ms）；Matcha 与 Phantom 表现平稳，但在展开起始阶段受 React 子树挂载影响存在约 120ms 的卡顿感知。
- **视觉体验**：展开时右上角按钮能够平稳避让原生窗口控件，但 Expo-Out 曲线过于陡峭，易产生“前冲后顿”感。

#### 场景 2：弹窗浮层 (Modals & Overlays)
- **现状评测**：设置弹窗呼出时存在不可避免的 200ms+ JS 同步阻塞。Doodle 的弹性回弹较好掩盖了卡顿感；Matcha 与 Phantom 缺少专属物理阻尼；Pixel 需将动画适配为阶梯步进定格，以彻底杜绝平滑插值带来的点阵字形发虚。
- **层级穿透严重缺陷**：Tooltip (`z-index: 9999`) 穿透弹窗遮罩 (`z-index: 5000`)，在弹窗内容上方高亮悬浮（详见 3.3 节）。

#### 场景 3：消息列表流式渲染与视窗跟随 (Streaming Message List & Follow)
- **机制实测**：`patch/pixelTheme.js` 中的 `STREAM_WATCH_JS` 通过 `MutationObserver` 监听 `document.documentElement`，配合 `IDLE_CHECK_MS = 500` 节流，有效抑制了空闲状态下的 DOM 查询风暴。
- **光标动画**：Pixel 的方块光标以 `steps(2, end)` 跳动，极具 8-bit 质感；然而 Matcha 与 Phantom 却直接继承了涂鸦主题的荧光粉方块光标（`--doodle-pink`），与静谧茶绿和波普怪盗红形成严重视觉冲突。

#### 场景 4：下拉菜单与级联选择框 (Dropdown Menus & Comboboxes)
- **组件行为**：Radix Popover 呼出平均耗时 7.08ms ~ 9.4ms，P50 锁定在 7.0ms，性能无瓶颈。
- **视觉缺陷实证**：
  - `doodle-theme` 中 Combobox 被强制赋予 `color: #FFFFFF !important;`，导致亮色模式下白底白字无法识别。
  - `phantom-theme` 中 Combobox 被直接抹除边框（`border: none !important; box-shadow: none !important;`），导致下拉框丧失可点击视觉线索（Affordance）。

#### 场景 5：交互微动效 (Micro-interactions: Hover, Active, Focus)
- **性格错位污染**：`matcha.css` 与 `phantom.css` 遗留了大量来自 Doodle 的 `@keyframes doodle-jiggle`（图标剧烈弹跳）与 `@keyframes doodle-nudge`（箭头反复撞击），使得和纸手帐的安宁感荡然无存。
- **粒子空跑实证**：发送消息时，`pixelTheme.js` 均会向 DOM 注入 16 个带有随机运动参数的 `<div id="px-particles"><i></i>...</div>` 节点。然而只有 `pixel.css` 实现了粒子方块样式，Doodle、Matcha、Phantom 中完全没有对应样式，导致 16 个 DOM 节点被空跑创建却对用户完全不可见。

#### 场景 6：持续背景动效与稳态功耗 (Background Visuals & Steady-state)
- **功耗评测**：空闲采样下单帧耗时紧贴 6.94ms，P50 锁定在 6.90ms，Long Task 均为 0。
- **表现细节**：Pixel 的 CRT 扫描线无显存常驻负担；Phantom 的 45° 斜纹与半色调网点为纯矢量图案，无持续重绘开销；AI 思考指示灯采用 1.6s 呼吸动效，相比二值硬闪更符合人眼工效学。

### 3.3 层叠上下文穿透与三大重大缺陷代码级根因

#### 缺陷 1：`trackDialogs()` 宿主漏检导致 Tooltip (`z-index: 9999`) 绝对穿透弹窗 (`z-index: 5000`)
- **现象实证**：在展开设置弹窗时，鼠标经过侧边栏图标残留的 Tooltip 浮层依然漂浮在设置弹窗的最上方（实测见 `test-reports/screenshots/doodle_06_settings_dialog.png`）。
- **代码级根因剖析**：
  在 `patch/pixelTheme.js` 第 653 行：
  ```javascript
  const onBody = (m.target === document.body);
  for (const n of m.addedNodes) {
    if (n.nodeType !== 1) continue;
    if (n.matches(DIALOG_SEL)) { openDialogs.add(n); touched = true; }
    else if (onBody) {
      const d = n.querySelector && n.querySelector(DIALOG_SEL);
      if (d) { openDialogs.add(d); touched = true; }
    }
  }
  ```
  1. **挂载宿主误判**：现场 CDP 深度探针实测，Antigravity 设置弹窗由 React 挂载在 `#root > div > div.h-full.w-full.dark` 下，**根本不在 `document.body` 根节点上**！
  2. **检测链路断裂**：当设置弹窗插入时，`m.target` 是内部深层容器，`onBody` 恒为 `false`；而 `n` 是遮罩层 `div.settings-modal-backdrop`，`n.matches(DIALOG_SEL)` 为 `false`（真正的 `[role="dialog"]` 是其内部子节点）。
  3. **标记完全丢失**：`openDialogs` 集合永远为空，导致 `<html>` 上 **永远未能添加 `px-modal-open` 类**！
  4. **抑制屏障变成死代码**：样式表第 3181 行的抑制规则 `html.px-modal-open [role="tooltip"] { display: none !important; }` 成为无用的死代码。加之 Tooltip 的 `z-index: 9999` 高于弹窗遮罩的 `z-index: 5000`，产生必然的视觉穿透。同时，修复此缺陷时必须严格保留原始实现中针对断链节点的 `!d.isConnected` 垃圾清理循环（`patch/pixelTheme.js:671-683`），以防 React 18 异步卸载 Portal 时因无直接 dialog 移除记录而发生状态永久卡死。

#### 缺陷 2：Section 22 HUD 街机角标 `body::after` 彻底破坏 Section 12 消息发送光柱
- **冲突实证定位**：
  - `pixel.css` 第 1678 行定义了用户发送消息时的数据包光柱动效：
    ```css
    html.px-sending body::after {
      content: "";
      position: fixed;
      bottom: 14vh;
      left: 50%;
      width: calc(8 * var(--px-dev));
      height: calc(14 * var(--px-dev));
      background: var(--primary);
      z-index: 2147483644;
      animation: px-packet var(--px-t-send) var(--px-ease-io) 1 both;
    }
    ```
  - 但在后续追加的 Section 22（第 3053 行），新增了全屏 HUD 瞄准角标：
    ```css
    body::after {
      content: "" !important;
      position: fixed !important;
      inset: 12px !important;
      pointer-events: none !important;
      z-index: 0 !important;
      opacity: 0.13 !important;
      background-image: url("..."), url("..."), ... !important;
    }
    ```
- **破坏机制与宿主层级错位**：
  由于第 3053 行位于样式表后部且带有全量 `!important`，其 `inset: 12px !important` 强行覆盖了 `bottom: 14vh; left: 50%`，`z-index: 0 !important` 覆盖了 `2147483644`。在所有四大主题中，**消息发送时光柱数据包动画被自身的背景角标彻底抹杀**！更深层的陷阱在于：`.px-sending` 状态类是由 `pixelTheme.js` 添加在 `<html>`（`document.documentElement`）而非 `<body>` 上，若修复规则误写为 `body:not(.px-sending)` 将因 `<body>` 从未携带此类而恒为真，角标依然无法阻断。必须精确从根节点判定 `html:not(.px-sending) body::after`。

#### 缺陷 3：Section 16 减动模式 (`prefers-reduced-motion`) 被后置 1800+ 行规则级联绕过与特异性击穿
- **无障碍失效实证**：
  在 `pixel.css` 第 2322-2429 行定义了 Section 16 `@media (prefers-reduced-motion: reduce)`，原作者批注：“*⚠ 这一节必须是全文件的最后一节*”。
  然而后续工程在第 2431 行至第 4200 行追加了 Section 17 ~ Section 24（包含顶部菜单、设置面板控件、斜杠联想浮层等），全部声明了带 `!important` 的动效规则。
- **W3C CSS Cascading Level 4 Step 5 特异性判定失效分析**：
  依据 W3C CSS Cascading and Inheritance Level 4 规范（Section 6.2），对于相同来源和优先级的声明（同属于 `Author !important`），浏览器按标准级联算法判定优先级：
  $$\text{Origin \& Importance} \to \text{Context} \to \text{Style Attribute} \to \text{Cascade Layers} \to \mathbf{Specificity (Step 5)} \to \mathbf{Order of Appearance (Step 6)}$$
  即浏览器**首先比对选择器特异性（Specificity，Step 5），只有当特异性完全一致时才进入源码声明顺序（Order of Appearance，Step 6）**。
  原通配选择器 `*, ::before, ::after` 特异性仅为 `(0, 0, 0)`。若仅使用常规根伪类选择器 `html:root body *`，其特异性三元组为：`:root` 伪类贡献 $B=1$；`html` 与 `body` 类型选择器贡献 $C=2$；通配符 `*` 贡献 $0$；整体特异性仅为 **`(0, 1, 2)`**。
  
  然而，后置追加的业务层组件规则广泛采用标签、类名与属性组合选择器：
  - `html body [role="dialog"].animate-modalScaleIn`：类型 2 (`html`, `body`)，属性 1 (`[role="dialog"]`)，类 1 (`.animate-modalScaleIn`)，特异性为 **`(0, 2, 2)`**；
  - `html[data-theme="pixel"] [role="dialog"].animate-modalScaleIn`：类型 1 (`html`)，属性 2 (`[data-theme="pixel"]`, `[role="dialog"]`)，类 1 (`.animate-modalScaleIn`)，特异性为 **`(0, 3, 1)`**；
  - `body.theme-pixel .settings-modal-container`：类型 1 (`body`)，类 2 (`.theme-pixel`, `.settings-modal-container`)，特异性为 **`(0, 2, 1)`**。

  **W3C 三元组严格字典序比对**：
  - 比对 $(0, 2, 2)$ vs $(0, 1, 2)$：$A$ 分量 $0 = 0$；$B$ 分量 $2 > 1$。业务规则 $(0, 2, 2)$ 严格胜出；
  - 比对 $(0, 3, 1)$ vs $(0, 1, 2)$：$A$ 分量 $0 = 0$；$B$ 分量 $3 > 1$。业务规则 $(0, 3, 1)$ 严格胜出。
  
  因为特异性在 Step 5 已产生绝对胜负，级联算法**根本不会进入 Step 6（源码后置顺序）**。无论将 `html:root body *` 挪到第几千行，在 Chromium 128 渲染引擎中，弹窗元素的 `animationDuration` 依然实测为 `0.24s`（240ms），用户在操作系统开启减动偏好时依然遭受全量剧烈缩放动画，直接违背 WCAG 2.1 SC 2.3.3。
- **ID 伪类否定 $(1, 1, 2)$ 降维压制方案**：
  为彻底压制任意业务层无 ID 选择器（$A=0$ 的任意 $(0, B, C)$ 组合），必须使减动选择器的首分量 $A \ge 1$。借助 W3C Selectors Level 4 规范中的 `:not()` 特异性继承机制，采用 **ID 伪类否定选择器**：
  `html:root:not(#_px_never_exist_) body *`
  根据 W3C Selectors Level 4 Section 16.1，`:not(S)` 的特异性等于其参数选择器 $S$ 的最大特异性。参数 `#_px_never_exist_` 贡献 ID 权重 $A=1$，`:root` 贡献 $B=1$，`html body` 贡献 $C=2$，生成数学级特异性 **`(1, 1, 2)`**。
  比对第一分量 $A$ 时，$1 > 0$ 恒成立，以数学绝对优势在 Step 5 降维压制所有业务层 `!important` 动效规则。

### 3.4 字体点阵可读性与 DPR 物理栅格同步机制

1. **DPR 物理网格对齐公式**：
   注入脚本 `DPR_SYNC_JS`（`patch/pixelTheme.js` 第 366-398 行）根据当前屏幕的设备像素比 `window.devicePixelRatio` 动态维护根变量：
   $$\text{--px-unit} = \frac{12}{\text{DPR}} \text{ px}, \quad \text{--px-cells} = \max(1, \text{round}(\text{DPR})), \quad \text{--px-dev} = \frac{1}{\text{DPR}} \text{ px}$$
   - 在 100% 缩放（DPR=1.0）下：正文字号计算为精确的 12.0px（占用 12 物理设备像素）；
   - 在 125% 缩放（DPR=1.25）下：正文字号计算为 `14.606px`（占用精确的 12 个物理设备像素格）；
   - 保证了无论系统缩放比例如何变动，Fusion Pixel 点阵字体的每个发光像素均严格映射在显示屏的单个物理晶体管栅格上。
2. **点阵字体严禁亚像素 `scale()` 插值**：
   在 `pixel.css` 第 2645-2654 行的 `@keyframes px-step-pop-in` 中，曾出现 `transform: scale(0.92) translateY(-6px);`。在 12px 点阵环境下，亚像素的缩放插值会导致光栅化引擎强行进行双线性双三次插值重采样，使原本锐利的像素字在动画中间帧呈现严重的模糊锯齿。**点阵字体的动效铁律为：只能使用整数设备像素的 `translateY(calc(-6 * var(--px-dev)))`，严禁使用连续 `scale()`**。
3. **高密汉字笔画拥挤与行高保障**：
   实测表明，在 12px 点阵格内渲染复杂中文汉字（如“徽”、“藏”、“籍”、“警”）时，字模仅有 $10 \times 10$ 像素的有效显示空间。若容器行高低于 `line-height: 1.5`（如默认的 `1.2`），汉字上下笔画将被严重挤压粘连，并在 `overflow: hidden` 下发生笔画切断。生产环境下正文与列表必须全局强制维持 `line-height: 1.5`（18px+）。
4. **抗锯齿模式严格分区**：
   - Pixel 主题必须强制 `-webkit-font-smoothing: none; image-rendering: pixelated;`，消除灰度平滑带来的边缘模糊；
   - Doodle / Matcha / Phantom 必须保留 `antialiased`，防止常规矢量字体产生严重毛刺。

### 4.2 P0 级方案：严重卡顿、主线程冻结与层级穿透修复

#### 【P0-1】修复 `patch/pixelTheme.js` 中 `trackDialogs()` 宿主漏检缺陷并保留 `!d.isConnected` 断链清理
- **所属文件**：`patch/pixelTheme.js` 第 649-684 行
- **技术原理**：
  1. **消除 `onBody` 漏检**：消除 `onBody = (m.target === document.body)` 这一硬编码限制。当 React 将设置弹窗挂载在深层容器（`#root > div > div.h-full.w-full.dark`）时，对 `addedNodes` 和 `removedNodes` 均执行深度扫描（`querySelector` / `querySelectorAll`），确保精准捕获 DOM 树任何深处的弹窗节点。
  2. **强制保留 `!d.isConnected` 垃圾回收循环**：React 18 卸载 Portal/弹窗时，经常通过替换或销毁上层容器实现，其生成的 `MutationRecord` 的目标往往是外部包装层，`removedNodes` 中往往不直接包含 `[role="dialog"]`。若删除 `!d.isConnected` 检查，已关闭弹窗将永久残留在 `openDialogs` 中，导致 `html.px-modal-open` 永久锁死，全应用所有 Tooltip 将永久消失！因此必须完整保留脱链节点的遍历清扫机制。
- **代码对照 (Before vs After)**：


#### 【P1-2】无障碍减动模式 `@media (prefers-reduced-motion)` 物理挪至末尾并强化特异性权重至 (1, 1, 2) (P1-7)
- **所属文件**：`pixel.css`, `doodle.css`, `matcha.css`, `phantom.css` 文件末尾
- **技术原理与 W3C CSS Cascading Level 4 Step 5 数学证明**：
  1. **W3C 层叠判定阶数算法 (Specificity > Order of Appearance)**：
     依据 W3C CSS Cascading and Inheritance Level 4 规范（Section 6.2），对于同属于 `Author !important` 优先级的多个冲突样式声明，浏览器按以下严格阶数仲裁：
     $$\text{Origin \& Importance} \to \text{Context} \to \text{Style Attribute} \to \text{Cascade Layers} \to \mathbf{Specificity (Step 5)} \to \mathbf{Order of Appearance (Step 6)}$$
     这意味着：**只有当 Step 5 的特异性三元组完全相等时，Step 6 的源码书写顺序才会产生仲裁效力**。
  2. **传统方案 `(0, 1, 2)` 的特异性劣势与 Chromium 实测击穿**：
     若仅在根部使用 `html:root body *`，其特异性三元组为 $(0, 1, 2)$（`:root` 伪类贡献 $B=1$；`html`、`body` 贡献 $C=2$）。
     然而业务层前置声明中广泛存在带有类和属性修饰的 `!important` 动画：
     - `html body [role="dialog"].animate-modalScaleIn` 特异性为 **$(0, 2, 2)$**；
     - `html[data-theme="pixel"] [role="dialog"].animate-modalScaleIn` 特异性为 **$(0, 3, 1)$**；
     - `body.theme-pixel .settings-modal-container` 特异性为 **$(0, 2, 1)$**。
     比对 $(0, 2, 2)$ 与 $(0, 1, 2)$：$A$ 分量 $0=0$；$B$ 分量 $2 > 1$，业务规则胜出；
     比对 $(0, 3, 1)$ 与 $(0, 1, 2)$：$A$ 分量 $0=0$；$B$ 分量 $3 > 1$，业务规则胜出。
     因业务规则的特异性严格更高，浏览器在 Step 5 直接判决业务动画声明生效，**根本不会进入 Step 6 源码顺序判定**。在 Chromium 128 实测中，弹窗元素在 `prefers-reduced-motion: reduce` 下计算出的 `animationDuration` 依然为 `0.24s`（240ms），减动无障碍要求全面击穿。
  3. **ID 伪类否定 `:not(#_px_never_exist_)` 的 $(1, 1, 2)$ 降维压制数学证明**：
     根据 W3C Selectors Level 4 规范（Section 16.1），`:not(S)` 伪类本身的特异性为其参数选择器 $S$ 的特异性。
     在选择器中引入虚拟不存在的 ID 否定器 `:not(#_px_never_exist_)`：
     - `#_px_never_exist_` 贡献 ID 计数 $A = 1$；
     - `:root` 贡献伪类计数 $B = 1$；
     - `html` 与 `body` 贡献类型计数 $C = 2$；通配符 `*` 贡献 $(0, 0, 0)$；
     - 最终特异性计算为：**$(1, 1, 2)$**（针对直接挂在根下的元素为 $(1, 1, 1)$，伪元素为 $(1, 1, 3)$）。
     
     **数学判定对比**：
     - $(1, 1, 2)$ vs $(0, 2, 2)$：$A$ 分量 $1 > 0 \implies (1, 1, 2) > (0, 2, 2)$；
     - $(1, 1, 2)$ vs $(0, 3, 1)$：$A$ 分量 $1 > 0 \implies (1, 1, 2) > (0, 3, 1)$；
     - $(1, 1, 2)$ vs $(0, N, M)$：对于任意没有直接绑定 ID 的业务规则（$A=0$），无论其拼接多少层类名或属性选择器，$1 > 0$ 恒成立！
     因此在 Step 5，减动规则以绝对特异性优势覆盖全部业务动效；配合物理移至样式表最底部（第 4200+ 行），即使面对极罕见含有 ID 的前置规则也能在 Step 6 兜底。
  4. **极小时间常数 `0.001ms` 规避动画生命周期中断**：
     将 `animation-duration` 与 `transition-duration` 设为 `0.001ms`（而非 `0s`），可使动画在单帧之内立即完成，同时确保标准的 `animationend` 和 `transitionend` 事件正常派发，防止依赖动效回调的 React 组件状态锁死。
- **代码对照 (Before vs After)**：

```css

    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}

  html:root:not(#_px_never_exist_) body *,
  html:root:not(#_px_never_exist_) body *::before,
  html:root:not(#_px_never_exist_) body *::after,
  html:root:not(#_px_never_exist_) *,
  html:root:not(#_px_never_exist_) *::before,
  html:root:not(#_px_never_exist_) *::after {
    animation-duration: 0.001ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.001ms !important;
    scroll-behavior: auto !important;
  }

    display: none !important;
  }
}
```

### 4.4 P2 级方案：微动效去污染、阻尼个性化与渲染细节收敛

#### 【P2-1】Matcha 抹茶主题重塑温润和纸落座动效（剥离 Doodle 涂鸦抖动）
- **所属文件**：`matcha-theme/matcha.css` (L1277-1280 等处)
- **技术原理**：
  1. **精确靶向子级动画载体**：`matcha.css` 中的 `doodle-jiggle` 与 `doodle-nudge` 实际上是挂载在 `button:hover > svg`、`[role="button"]:hover > svg` 等**子级 SVG 图标与 span 节点**上，而非按钮本体。若仅给 `button:hover` 设置 `animation: none`，子元素依然会按更高特异性规则剧烈震颤。必须精确靶向 `button:hover > svg, button:hover > span` 等子节点将其动画彻底置为 `none !important;`。
  2. **专属和纸物理阻尼**：建立抹茶专属的纸张衰减阻尼曲线 `--matcha-ease-paper: cubic-bezier(0.25, 1, 0.5, 1)`；改用优雅的 1px 微下沉按压触感反馈，使和纸手帐的安宁治愈质感完全归位。
- **代码对照 (Before vs After)**：


### 5.5 判废与基准失效条件 (Invalidation Conditions)

若在后续实施与复测中发生以下任一现象，表明系统基准发生偏移或方案未达预期，需判定回归失败并打回整改：
1. **DPR 栅格脱位**：若在 125% 或 150% 缩放比下，Fusion Pixel 点阵字体的边缘出现灰度渐变杂色，说明 `DPR_SYNC_JS` 网格计算失效或引入了亚像素 `scale()` 插值。
2. **弹窗漏检与状态锁死**：若在打开设置弹窗时，`document.documentElement.classList.contains('px-modal-open')` 依然返回 `false`；或在关闭弹窗后因缺失 `!d.isConnected` 清扫而导致 `px-modal-open` 无法移除，判定为追踪逻辑缺陷。
3. **光柱再次被淹没**：若在触发发送消息时，`html.px-sending body::after` 未能在视窗 14vh 处呈现向上升空的光柱，或修复规则误用 `body:not(.px-sending)`，说明伪元素选择器层级冲突依然存在。
4. **流式重算惩罚复发**：若在全局 CSS 方案中重新引入 `body:has([role="dialog"])` 等高开销祖先失效选择器，导致聊天流式输出时 RecalcStyle 耗时翻倍，判定为违反性能设计红线。
5. **主题艺术动效遭同质化**：若将和纸手帐或波普怪盗的弹窗动效强行替换为 8-bit `steps(3)` 阶梯步进，或在像素主题中引入圆角与高斯模糊阴影，判定为严重违反“不改变现有设计风格”的硬性承诺。
6. **无障碍对比度虚假达标**：若 Phantom 亮色推荐的强调色在冷灰白底色 `#F4F4F6` 上实测相对对比度仍低于 $4.5:1$（如继续使用 `#B8860B` 2.96:1 而非 `#8A6300` 4.95:1），判定为无障碍审查未通过。
7. **减动特异性被后置规则覆盖**：若操作系统开启 `prefers-reduced-motion` 后，设置弹窗或会话列表依然触发完整动画，说明通用减动规则特异性不足（未达 (1, 1, 2) 绝对压制权重），未能压制带有类/属性选择器的 `!important` 业务规则。
